# Kilo Code on the V100

Status on 2026-10-28: Kilo Code 7.8.18 on the Mac completed a real text request through `llamafarm-v100/qwen3.8:27b`. Its MCP server connected. The V100 gateway was healthy. Later that day, 128K and 256K aliases of the same 27B weights were created in the bundled Ollama server. The 256K alias is now the LlamaFarm and Kilo default. Ollama reported `CONTEXT 262144` and `100% GPU` while serving it. The deployed bundle checkout was `d52397f` on the `v3` line. The Rust gateway changes in this branch are local until reviewed and deployed.

## Client setup (macOS and Linux)

1. Install VS Code and the maintained `kilocode.Kilo-Code` extension: `code --install-extension kilocode.Kilo-Code`.
2. Clone this repository at the branch used by the V100. Create a client Python environment: `python3 -m venv tools/llamafarm_mcp/.venv && tools/llamafarm_mcp/.venv/bin/python -m pip install -r tools/llamafarm_mcp/requirements.txt`.
3. Copy [the Kilo configuration template](../tools/llamafarm_mcp/kilo.example.json) to `~/.config/kilo/kilo.jsonc`. If that file exists, merge the fields instead of replacing other settings. Replace the two `/ABS/PATH/TO/...` entries with absolute client paths. On macOS and Linux the config directory is the same. No cloud API key or subscription is required.
4. Use SSH key authentication to `USER@TAILSCALE_HOST`. On this Mac, the installed LaunchAgent keeps the tunnel connected. On another client, set `LLAMAFARM_SSH_TARGET=USER@TAILSCALE_HOST` and run `scripts/kilo/ollama-tunnel.sh` in a terminal while using Kilo. It binds only `127.0.0.1:11435` and forwards to Ollama on the V100's loopback interface over Tailscale. `LLAMAFARM_LOCAL_OLLAMA_PORT` overrides the local port.
5. Reload the VS Code window. Open Kilo Code and select `llamafarm-v100/qwen3.8:27b-256k` in the model picker. Existing sessions can retain a prior model pick; create a new session or change the pick explicitly. The template's `enabled_providers` admits only `llamafarm-v100`, so `kilo-auto/free` cannot answer a request.

The model connection and MCP connection are separate. Kilo sends Chat Completions to Ollama through the SSH tunnel. It starts `server.py` locally over stdio; that bridge calls the LlamaFarm gateway at `http://TAILSCALE_HOST:42617`. The bridge exposes `llamafarm_agent`, `llamafarm_agent_batch`, `llamafarm_chat`, `llamafarm_run_status`, and `llamafarm_tools_catalog` without changing the existing MCP implementation. The Kilo provider is direct Ollama until the gateway API changes in this branch are deployed and verified. Kilo's `limit.context` controls its compaction threshold. The Ollama alias supplies the actual 256K context for OpenAI-compatible requests; see [its Modelfile](../deploy/models/qwen3.8-27b-256k.Modelfile). Create it on a new node with `ollama create qwen3.8:27b-256k -f deploy/models/qwen3.8-27b-256k.Modelfile` after the base 27B model is installed. The 128K alias remains available as a lower-VRAM choice.

If Kilo reports **connection reset**, check `ssh USER@TAILSCALE_HOST 'curl -fsS http://127.0.0.1:11434/api/tags'`. A tunnel can stay open while Ollama is stopped. Restart the existing LlamaFarm bundle only when the V100's other workload is clear; the tunnel then reconnects without exposing Ollama publicly. On this Mac, a LaunchAgent under `~/Library/LaunchAgents` keeps the tunnel connected through SSH drops and logins. Use `kilo config check`, `kilo models`, and `kilo mcp list` from the extension's bundled `bin/kilo` to check the client. A model list or MCP handshake alone does not prove inference; send a short Kilo prompt and inspect its session log for `llm.provider=llamafarm-v100`.

## Agent behavior

Code, Plan, and Debug are pinned to the V100 model. Review is read-only. The client automatically permits repository reads, file finding, and searches, with sensitive file patterns requiring approval. Edits, shell commands, external directories, delegated tasks, and MCP actions prompt in **Settings → Auto Approve**. Do not enable `--auto` or a universal `allow` rule. Use Agent Manager worktrees for independent tasks, give each worker separate files, and accept results only after inspecting diffs and test output. These rules follow [Kilo's current provider](https://github.com/Kilo-Org/kilocode/blob/main/packages/kilo-docs/pages/ai-providers/openai-compatible.md), [MCP](https://github.com/Kilo-Org/kilocode/blob/main/packages/kilo-docs/pages/automate/mcp/using-in-kilo-code.md), [permissions](https://github.com/Kilo-Org/kilocode/blob/main/packages/kilo-docs/pages/automate/how-tools-work.md), and [Agent Manager](https://github.com/Kilo-Org/kilocode/blob/main/packages/kilo-docs/pages/automate/agent-manager.md) documentation.

## Current hardware evidence and benchmark

The host has one Tesla PG500-216 V100 with 32,768 MiB VRAM and 123 GiB system RAM. The Kilo text probe returned `V100-OK-28`. [The 2026-10-28 benchmark](benchmarks/v100-2026-10-28.md) measured four installed models, warm and cold loads, a 7,697-token prefill, tool calls, context allocation, and two-request queueing. A 256K allocation probe completed 160 output tokens at 54.6 tok/s. An uncached 7,720-token prompt prefetched at 705 tok/s with 29,406 MiB peak sampled GPU memory. Ollama reported 100% GPU and a 262,144-token context. A full 256K-token input has not been timed or quality-tested.

The Kilo CLI 256K smoke turn took about 34 seconds and its session export recorded 20,444 input tokens and 59 output tokens. It made no MCP tool call. The large agent prompt accounts for most of that delay; direct Ollama tests with short prompts do not measure a Kilo turn. Keep MCP enabled for LlamaFarm's agent tools, but it is not in the direct model request path. No separate LlamaFarm gateway hop is used for Kilo model inference.

## Dual V100 and Flash Next

Only one V100 is currently visible. A second card should run a separate Ollama worker pinned by its GPU UUID, with a distinct private endpoint, health check, model residency, and queue. Route independent coding and review jobs to separate workers after checking VRAM. A combined-GPU worker should start only when both cards are idle, with explicit operator action and separate measurements; two cards do not imply faster single-stream decoding.

Qwen3.8-Flash-Next remains experimental. The [Ollama Q8 listing](https://ollama.com/library/qwen3.8-flash-next:125b-a6b-q8_0) is 189 GB and cannot be a default V100 model. A [separate IQ4 n-gram table](https://huggingface.co/Delgon/Qwen3.8-Flash-Next-PLE-GGUF) is about 28.8 GB, and [llama.cpp's discussion](https://github.com/ggml-org/llama.cpp/discussions/27864) describes split-table modes. [llama.cpp issue #28355](https://github.com/ggml-org/llama.cpp/issues/28355) documents that `--lazy-mode off -ot per_layer_token_embd=CPU` keeps the large table resident in system RAM; lazy loading can hurt prefill when the page cache is evicted. An IQ4/Q4 compute quant still needs model weights, KV cache, and scratch memory beyond the table. There is no verified Volta CUDA throughput or single/dual V100 memory measurement for this model here, so it is not installed or enabled.

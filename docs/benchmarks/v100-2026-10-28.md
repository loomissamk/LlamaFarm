# V100 inference benchmark — 2026-10-28

Host: `USER@TAILSCALE_HOST` over Tailscale. GPU: Tesla PG500-216, 32,768 MiB. Inference server: the running Ollama instance behind LlamaFarm. LlamaFarm health was OK and TerminAI training was inactive before the run. All four models were already installed; no model was downloaded or modified.

These are **direct Ollama `/api/chat`** measurements, so they exclude Kilo, the LlamaFarm gateway, SSH tunnel, and MCP overhead. Requests were serial except for the explicit two-request test. Each text request asked for a numbered Rust code review list with `think=false`, `temperature=0`, `num_predict=160`, and `num_ctx=8192`. The four 27B warm rows use the same prompt and context. Decode rate is Ollama's `eval_count / eval_duration`; wall time includes loading, prefill, decoding, and API overhead. GPU memory is sampled with `nvidia-smi` every 0.5 seconds and is approximate.

| Model | Parameters / quantization | Warm 160-token wall time | Warm decode | Resident GPU memory | First request after switch |
| --- | --- | ---: | ---: | ---: | ---: |
| 27B dense | 27.3B / Q4_K_M | 3.00–3.21 s (4 runs) | 55.0–55.4 tok/s | 18,446 MiB at 8K | 7.33 s; 4.13 s load |
| 9B dense | 9.7B / Q4_K_M | 1.78 s | 93.3 tok/s | 6,730 MiB | 5.56 s; 3.76 s load |
| 35B coding MoE | 35.5B / Q4_K_M | 1.08 s | 158.2 tok/s | 22,650 MiB | 5.83 s; 4.61 s load |
| 80B MoE | 79.7B / Q4_K_M | 3.24 s | 51.1 tok/s | 31,222 MiB | 9.90 s; 6.24 s load |

Installed model IDs, in table order: `qwen3.8:27b`, `qwen3.5:9b`, `qwen3.6:35b-a3b-coding-mtp-q4_K_M`, and `qwen3-next:80b-a3b-instruct-q4_K_M`.

The 35B coding MoE is the speed winner for this particular 160-token prompt. This benchmark does not measure answer quality or code-editing success. The 80B model's 50.1 GB file exceeds the 32 GB GPU, so its 31.2 GiB GPU allocation is not evidence of full GPU residency.

## 27B details

- Changing `num_ctx` among 8K, 16K, 32K, and 64K kept decode near 55 tok/s on the same 43-token prompt. Each change reloaded the runner for about 4 seconds. This tests context allocation and short-prompt speed; it does not test 64K-token input quality or prefill.
- An additional 7,697-token prompt at `num_ctx=32768` prefetched at 842 tokens/s. The request took 13.50 seconds end to end, including 3.94 seconds of runner reload. It produced 19 output tokens before stopping.
- A single structured `record_probe` tool call returned the requested argument correctly on all four models. This is a smoke test, not a tool-use accuracy evaluation.
- Two concurrent warm 27B text requests returned 320 total tokens in 6.05 seconds, or 52.9 aggregate tok/s. One finished in 3.04 seconds and the other in 6.05 seconds. They queued on the single model runner rather than doubling throughput.
- The 27B used about 18,446 MiB at 8K, 19,450 MiB at 32K, and 20,566 MiB at 64K in sampled GPU memory. Context allocation changes memory use; actual long-input behavior remains unmeasured.
- A later 128K allocation probe completed 160 output tokens at 55.1 tok/s, with 23,382 MiB peak sampled GPU memory. Ollama reported `context_length=131072` while serving the new `qwen3.8:27b-128k` alias. This confirms allocation and short-prompt operation at 128K; a full-length 128K input has not been timed or quality-tested.

The benchmark run restored `qwen3.8:27b` as the resident model at the original 32K context. After the 128K probe, LlamaFarm's persistent default model was changed to the alias. LlamaFarm remained healthy afterward.

## Qwen3.8 27B at 128K and 256K

The base `qwen3.8:27b` model reports a native 262,144-token context. The V100 runs the same Q4_K_M weights through `qwen3.8:27b-128k` and `qwen3.8:27b-256k` aliases. The bundled Ollama server has Flash Attention and q8_0 KV cache enabled. These results use one runner and direct Ollama requests; Kilo and MCP add their own overhead. The 256K prefill run used a unique nonce to bypass prompt caching.

| Context | Warm prefill, 7.7K input | 160-token decode | GPU peak |
| --- | ---: | ---: | ---: |
| 128K | 707 tok/s (11.36 s) | 55.0 tok/s | 23,774 MiB |
| 256K | 705 tok/s (11.67 s) | 54.6 tok/s | 29,406 MiB |

The 256K short-output probe took 7.54 seconds with a 4.28-second runner reload; its measured decode rate excludes the reload. The warm 256K prefill had a 1.5 ms load time. Ollama reported `100% GPU` and `CONTEXT 262144` after the 256K run. The peak leaves about 3,362 MiB of the V100's 32,768 MiB available. Allocating 256K uses much more VRAM even for a shorter prompt, but 128K and 256K had nearly identical prefill rates for this 7.7K-token input. Much longer input will take longer to prefill and may alter memory pressure; a full 256K-token input and coding quality at that length have not been tested.

The live LlamaFarm default and Kilo Code, including its MCP model setting, now use `qwen3.8:27b-256k`. A Kilo CLI request returned `V100-256K-KILO-OK`; LlamaFarm health remained OK. The 128K alias remains selectable in Kilo. The 35B coding MoE was faster in these short-output tests, but no code-editing quality comparison establishes it as better for this setup. The 27B dense model remains the default.

The Kilo CLI smoke turn took about 34 seconds after opening its session. Its exported usage recorded 20,444 input tokens and 59 output tokens, with no tool calls. That input size explains most of its delay at the measured prefill rate. The direct Ollama rows above use much shorter prompts and therefore are not end-to-end Kilo latency measurements. The test does not isolate how much of Kilo's prompt came from its core instructions, tool definitions, or MCP registration.
